# Curation

## Language

**Check**: A repeatable question about the quality of a named build. Its result can motivate a finding but does not itself decide a correction.

**Finding**: A documented observation about source data or the project's processing, with evidence and attribution. Its origin distinguishes a source finding from a processing defect.

**Curation case**: The durable record connecting a finding, its proposals, relevant modules, validation and review history. A case can retain rejected proposals and withdrawn conclusions.

**Review package**: A named set of cases that share a review question and an explicit grouping rationale. Cases retain their identities and evidence when a package is split or regrouped.

**Triage acknowledgement**: A person's recorded acknowledgement of a package's scope and next action, with any cases requiring separate attention. It does not establish scientific approval, execution or adoption; changed membership or evidence requires renewed triage.

**Triage exception**: A case explicitly held for individual attention when the surrounding package is acknowledged. It stays visible as unresolved work.

**Workstream**: A collection of review packages concerning the same broad part of the curation work, such as method policies or historical comparisons.

**Proposal**: A suggested response to a finding, discussed in an issue, discussion or pull request. Several proposals can concern one finding.

**Correction module**: Existing executable code, with any curated decisions it consumes, that applies a defined change. One module can answer several cases, and a case can require several modules.

**Sign-off**: A named person's recorded judgement about a precise revision and scope. Code review and scientific acceptance are different scopes; changing the reviewed revision makes a sign-off stale.

**Validation receipt**: A recorded execution of checks against identified code and inputs, with its result and limits. The existence of a test is not a validation receipt.

**Release adoption**: Evidence that a named published build contains and applies a revision. Merging a proposal or passing focused tests does not establish adoption.
